# ChEMBL activity projection — measured cost (2026-09-16)

Raw records: `online00-chembl-projection-2026-09-16.json` (generated by
`services/core/benchmarks/chembl_projection.py`, not hand-written).

The ONLINE-00 discovery adapter fetches ChEMBL activities with an explicit field
projection (`ChEMBLDiscoveryAdapter.ACTIVITY_FIELDS`). This record measures what
that projection actually buys, and — more usefully — what it does not.

## How this was produced

```bash
cd services/core
python benchmarks/chembl_projection.py \
  --target-chembl-id CHEMBL3712931 --target-chembl-id CHEMBL203 \
  --pages 2 --repeat 2 --out ../../benchmarks/online00-chembl-projection-2026-09-16.json
```

The harness imports `ACTIVITY_FIELDS` and `PAGE_LIMIT` from the adapter, so the
projected variant cannot drift from what the product sends. The "full" variant is
the same request without `only=` — the counterfactual, not a different endpoint.
Requests alternate full/projected within each page, so a slow minute on EBI's side
hits both variants.

`CHEMBL3712931` is TSLP's activity set (114 activities, one page — the pair the
adapter test cites). `CHEMBL203` is EGFR (many pages, the multi-page case).

## Transfer: the projection saves about 42 %

| Target | Full (bytes/page) | Projected | Saving | Keys/record |
| --- | --- | --- | --- | --- |
| CHEMBL3712931 (TSLP) | 216,632 | 127,415 | **−41.2 %** | 47 → 25 |
| CHEMBL203 (EGFR) | 297,821 (median) | 169,798 (median) | **−43.0 %** | 47 → 25 |

Same record counts in both variants (114 and 200 per page) — the projection
removes keys, not rows.

## Latency: **no improvement measured, and the projected variant was slower**

| Target | Full median | Projected median | Delta |
| --- | --- | --- | --- |
| CHEMBL3712931 (TSLP) | 1,273 ms | 1,304 ms | +31 ms (inside noise) |
| CHEMBL203 (EGFR) | 1,091 ms | 2,041 ms | **+950 ms** |

The CHEMBL203 samples are consistent across the interleaved repeats (full
883–1,831 ms; projected 1,679–2,913 ms) and across two runs of this harness. The
smaller response did **not** arrive sooner; the server appears to spend more time
producing a projected page than a full one.

**This is the number that changes a documented claim.** `bindingdb-io-port` §6.5
called the full activity payload "the dominant upstream cost". The transfer is the
dominant *bandwidth* cost, and the projection cuts it by ~42 %. It is not the
dominant *latency* cost: the page count is. A 2,000-activity target
(`max_activities`) is ten projected pages at roughly 1.7–3 s each — the number of
round trips, not the size of each one, decides how long an investigation waits.

## What these numbers do and do not say

- They are single upstream requests from one host at one time, not application
  latency, and not a capacity claim. EBI's response time varies with load.
- The byte saving is exact for these targets at `limit=200` (identical record
  counts, byte-identical repeats); a differently shaped activity set would move
  the percentage.
- The latency observation is an **observation**, not an explanation. The cause was
  not investigated; the web services expose no timing breakdown.
- No decision follows from this about reverting the projection. It is kept: it
  reduces egress for the deployment and is pinned by a test. The claim attached to
  it changes from "cheaper" to "smaller", and the latency claim is withdrawn.
- The remaining upstream-latency lever is the number of pages
  (`max_activities`), which is a product decision about coverage — not something
  this measurement authorizes changing.
