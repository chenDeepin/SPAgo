# ADR-0001: M0 foundation data path and infrastructure choices

Date: 2026-09-14. Status: ACCEPTED (implemented in M0).

## Context

Milestone 0 requires a reproducible, one-command local deployment
(PROMPT.md §14 exit criteria) including "PostgreSQL + RDKit", a SureChEMBL Parquet
fixture queried through DuckDB, and a benchmark harness — without introducing
services banned pending evidence (AGENTS.md §6) and without duplicating bulk data
into PostgreSQL (AGENTS.md §7).

## Decisions

### 1. Two-container deployment

`db` (PostgreSQL 15 + RDKit cartridge) and `app` (FastAPI serving the built React
bundle). No reverse proxy, no orchestration tooling at M0.

### 2. Build the PostgreSQL+RDKit image from Debian, not a third-party image

No actively maintained, trustworthy PostgreSQL+RDKit cartridge image exists on
Docker Hub (`rdkit/rdkit_postgres` is gone). Debian bookworm ships a consistent
pair: `postgresql-15` + `postgresql-15-rdkit` (RDKit 202209.3 cartridge). We build
`docker/db` from `debian:bookworm-slim` with those packages and a minimal
entrypoint. The cartridge is installed at DB-init time (`CREATE EXTENSION rdkit`)
but M0 does not yet build cartridge indexes — that arrives with M2 structure search.

Alternatives rejected: community images (unmaintained/unknown provenance);
compiling the cartridge from source (heavy, slow builds); postgres:15 official
image + foreign distro package (ABI/config mismatch risk).

### 3. Fixture ingestion: adapter → RDKit normalization → PostgreSQL

The synthetic fixture emulates a simplified SureChEMBL extract (Parquet). A
`ChemicalPatentSource` adapter reads it through DuckDB and returns normalized
domain models plus a source envelope. Seeding canonicalizes chemistry with RDKit
(dedupe by InChIKey, preserve per-document mentions, record malformed structures
as warnings). PostgreSQL is the serving store for the interactive workflow.

Rationale: proves the full contract chain (adapter isolation, deterministic
chemistry, provenance, migrations) on data small enough to verify by eye, without
making PostgreSQL a bulk-data copy — the adapter path is the same one a real
SureChEMBL release would flow through.

### 4. Plain-SQL migration runner instead of Alembic

Migrations are ordered, non-revisable SQL files applied by a ~80-line runner that
records applied versions in `schema_migrations`. Transparent, zero extra
dependency, forward-testable from zero. If migration ergonomics (branching,
downgrades, autogenerate) become a real cost, an ADR will revisit this.

### 5. Server-side depictions

Molecule depictions are RDKit SVGs generated by the backend per compound request
and cached on disk. The browser never draws or parses structures. This follows the
UI direction doc ("结构图必须由后端 RDKit 生成") and keeps depiction cost measurable
(benchmarked cold/warm).

### 6. Provenance labeling of the fixture

Fixture rows are synthetic. They carry `dataset_version = demo-fixture-v1`,
`extraction_method = surechembl_simplified_fixture`, provenance state
`machine_extracted` (modeling what a bulk extract is), and the UI labels the
dataset as demo data. Synthetic data must never be presented as real patent facts.

## Consequences

- Startup: `docker compose up -d --build` → healthz green → demo patent searchable.
- First build is heavy (RDKit wheel); acceptable.
- When real SureChEMBL releases are ingested, the adapter gains a download/refresh
  job and dataset versioning metadata; the serving model should not change.
- PG15 + cartridge 202209.3 pins chemistry SQL behavior; M2 must record which
  cartridge operators/indices it relies on.
